# 系统架构

## 总体概览

整个系统分为四层：

1. 硬件与厂商运行时层
2. ROS2 应用层
3. API / WebSocket 网关层
4. 浏览器控制台层

Yahboom 小车已经提供了底层平台能力，包括树莓派 5、micro-ROS 控制板、雷达、摄像头和运动底盘。本项目在此基础上增加一层面向产品使用的编排层，同时避免让浏览器直接依赖原始 ROS 话题。

## 分层说明

### 1. 硬件与厂商运行时层

这一层负责：

- 雷达扫描采集
- 摄像头视频流采集
- 底盘运动控制与里程计
- IMU 与底层状态
- 通过串口或 USB 访问 ESP32 micro-ROS 控制板

基本假设：

- Yahboom 小车已经提供稳定的 ROS2 兼容话题或桥接节点，用于底盘控制、雷达、图像、里程计等能力。

### 2. ROS2 应用层

`ros2_ws/src` 下的自定义包应当承载业务行为，而不是把浏览器逻辑塞进 ROS2 节点中。

规划中的包包括：

- `rover_interfaces`：共享消息与服务定义
- `rover_bringup`：启动文件与公共参数编排
- `rover_mapping`：建图会话管理、占据栅格导出、点云转换、3D 场景元数据
- `rover_navigation`：目标点下发、区域路由、路径执行、任务编排
- `rover_safety`：避障、安全限速、虚拟墙、禁行区域
- `rover_ai_bridge`：AI 指令解析与任务翻译
- `rover_voice_bridge`：浏览器音频桥接、唤醒词、ASR、TTS 适配

### 3. API / WebSocket 网关层

这一层存在的原因主要有两个：

- 浏览器需要一个稳定的协议层，不能直接绑定 ROS 话题细节
- 语音、AI、鉴权与限流等能力更适合放在服务端，而不是前端

主要职责：

- 暴露任务、地图、区域、语音等接口
- 通过 WebSocket 广播遥测快照
- 将地图、位姿、雷达、相机元数据整理成前端友好的结构
- 在生产环境中托管前端静态资源

### ROS2 与 Web 的结合点

后续接入真实小车时，建议坚持一个清晰边界：

- ROS2 负责建图、定位、路径规划、底盘执行
- API 负责协议收敛、状态缓存、权限与合法性校验
- Web 负责地图交互、轨迹可视化、标签编辑和任务操作

这样浏览器不需要直接理解 ROS2 话题细节，只需要面对稳定的 REST / WebSocket 协议。

### 4. 浏览器控制台层

UI 采用单屏操作台设计，而不是多页跳转式后台。

布局分区：

- 地图工作区始终占据主区域，并固定为不可旋转的俯视视角
- 小车状态、运行控制、相机画面以浮动 HUD 的方式叠加在地图上
- 任务队列与“区域 / 虚拟墙”通过 ICON 弹窗按需打开，而不是常驻侧边栏
- AI 对话与历史记录收敛成一个紧凑的底部会话窗，方便查看小车 AI 的上下文

这样做的目的，是让操作者始终停留在同一视图内，把地图作为核心交互中心，同时保证所有能力尽量在一屏内完成。

当前浏览器层还需要显式覆盖两类状态：

- 未建图态：地图区域为空，显示建模提示 ICON 和“一键全屋扫描”按钮
- 建图完成态：开放区域标签编辑、虚拟墙绘制、右键导航和轨迹预览

## 建图与 3D 空间重建

数据流大致如下：

1. `slam_toolbox` 或兼容 SLAM 节点根据雷达扫描构建占据栅格地图。
2. `rover_mapping` 保存建图会话，并导出：
   - 占据栅格
   - 地图元数据
   - 障碍物多边形
   - 墙体线段
   - 可通行区域
3. 前端再将这些数据转换成：
   - 用于编辑与遥测叠加的 2D 地图层
   - 一个受 `build-house` 启发的简化 3D 房间/空间网格

关键限制：

`MS200` TOF 雷达本质上只支持 2D 建图，并不是完整的 3D 体素扫描。因此这里的 3D 视图只能由 2D 地图几何和语义区域数据推导出来，而不能被当作真实三维扫描结果。

### 未建图态与一键全屋扫描

浏览器不应在“还没有地图”的情况下继续展示伪造的区域内容。更合理的行为是：

1. 地图区呈现空态和建模提示，而不是预置区域卡片。
2. 操作者点击“一键全屋扫描”后，小车进入全屋自动避障扫描流程。
3. 扫描完成后，前端再解锁区域标签、虚拟墙和导航相关交互。

这样可以让产品状态和真实机器人能力保持一致，避免操作者在未建图时误以为已经可以直接导航。

### 接入真实 SLAM 建图

后续接入实车时，建图链路建议固定为：

1. `slam_toolbox` 或兼容 SLAM 节点持续发布 `OccupancyGrid`、`map_metadata` 和定位结果。
2. `rover_mapping` 负责把这些原始结果整理成 Web 需要的地图边界、区域多边形、墙体线段和可通行区。
3. API 再把地图快照、建模进度和地图版本通过 REST / WebSocket 暴露给前端。
4. Web 根据建图状态切换未建图空态、建图中进度态和建图完成后的交互态。

关键点是：Web 端看到的“区域”和“墙体”应来自真实地图重建结果，而不是长期停留在前端 mock 数据。

## 导航与安全

导航层的设计假设如下：

- Nav2 负责路径规划与局部控制
- keepout filter / 虚拟墙会被转换为 costmap 约束
- `rover_safety` 可以接管急停、局部减速和操作员告警
- 浏览器允许操作者右键地图设置目标点，但该目标点仍然要先经过路径合法性校验和 keepout 约束检查
- 浏览器侧会预览一条轨迹，供操作者确认小车将如何绕开虚拟墙和限制区

安全行为约束：

- 即使是 AI 驱动的任务，也必须持续开启本地避障
- 虚拟墙优先级高于 AI 指令
- 浏览器发来的导航命令必须先经过合法性校验，再转换为导航目标

### 区域标签与虚拟墙

地图编辑不应只停留在“选中预置区域”。当前交互设计要求前端至少支持：

- 区域标签的增、删、改，用于给不同区域命名并直接显示在地图上
- 在地图上通过两点绘制虚拟墙线段，作为临时隔离和 keepout 输入
- 当虚拟墙变化时，已有导航轨迹应尽量触发重规划，避免轨迹显示和安全边界不一致

### Nav2 导航与 Web 路径规划

为了让 Web 路径规划真正和小车一致，建议按下面的方式接入：

1. 浏览器右击目标点、节点规划、区域目标，统一发送给 API。
2. API 校验目标是否落在可通行区域内，是否穿越 keepout / 虚拟墙，再转交 `rover_navigation`。
3. `rover_navigation` 再把请求映射到 Nav2 的 `NavigateToPose` 或 `NavigateThroughPoses`。
4. Nav2 返回的真实规划路径应回流到前端，用来替换浏览器本地预演路径。

这样前端的路径显示就不是“估算出来的动画”，而是真正会被底盘执行的导航结果。

### 实时轨迹展示

轨迹展示建议始终基于 ROS2 的真实位姿序列，而不是前端自己推进：

- `odom`、`tf`、定位状态和当前任务状态进入 API
- API 通过 WebSocket 连续广播当前位置、历史轨迹点和当前规划路径
- Web 在地图上叠加：
  - 当前小车位置与朝向
  - 已行驶历史轨迹
  - 当前待执行路径
  - 目标点 / 节点 / 虚拟墙

只要这几类数据都来自后端统一快照，浏览器展示和小车真实运动就不会逐渐偏离。

## AI 指令链路

基本流程：

1. 操作员在 Web 控制台输入自然语言指令
2. API 接收命令
3. `rover_ai_bridge` 将意图转成结构化任务
4. `rover_navigation` 或其他领域节点执行这些任务
5. 任务状态持续回流到浏览器

示例：

`去客厅巡检并汇报异常`

会被拆成：

- 导航到 `living_room` 区域
- 启动相机/雷达巡检策略
- 汇总异常结果
- 按需语音播报结果

### 整屋垃圾扫描与 OpenClaw 上报

“贾维斯，请帮我扫描整个房屋，发现有垃圾请拍照告诉我”会在 AI 桥接层生成一个 `whole_home_scan` 任务。ROS2 感知组件会执行全屋扫描，发现垃圾后产生 `GarbageDetection` 载荷（包括 `task_id`、房间标签、描述、图片 URL），然后用 `POST /api/v1/garbage/detections` 把报告送到 API。

API 负责拼接 `ROVER_OPENCLAW_WEBHOOK_URL` 的 webhook 请求体，OpenClaw 接到后在飞书群发布一个卡片，卡片里包含照片、房间信息、任务状态以及清理提醒。整个链路的任务状态会覆盖前端任务列表和系统快照，保证操作员能看到指令的执行进度。

在当前实现里，ROS2 侧由新增的 `rover_vision` 包承担视觉检测职责：

- 订阅 `/camera/image/compressed` 或 `/camera/image_raw`
- 使用 `ultralytics` YOLO 模型做垃圾类标签过滤
- 将抓拍图保存到本地目录，并同步保存 sidecar JSON 元数据
- 通过 `/api/v1/system/snapshot` 轮询当前活跃的 `whole_home_scan` 任务
- 命中目标后调用 `/api/v1/garbage/detections` 回灌检测结果

考虑到树莓派部署差异，`rover_vision` 默认不在 bringup 中启用，只有在模型文件、Python 依赖和相机话题都准备好时才打开。当前默认参数已经转向 TACO 数据集工作流：

- 模型权重默认指向 `taco_pi_best.pt`
- 标签映射支持 TACO 官方 `class_map` CSV
- 在树莓派上默认开启 `pi_mode`、抽帧和缩图

这样做的目标，是兼容 TACO 的多类别识别，同时把推理成本控制在 Pi5 可接受的范围内。

## 树莓派上的语音策略

语音能力默认是可选项，因为树莓派 5 的算力依然有限，不能让语音推理影响导航和建图主链路。

推荐路径：

- 唤醒词与 ASR：`sherpa-onnx`
- 可选 TTS：`sherpa-onnx` TTS 适配
- 浏览器回退模式：网页侧麦克风采集 + 按键说话

运行原则：

- 默认部署关闭唤醒词
- 只有在目标树莓派上确认模型延迟可接受时，才启用唤醒词 / ASR / TTS

## 部署模型

开发环境：

- 前端与 API 分容器运行
- ROS2 运行时可按需使用 host network

生产环境：

- 一个主机器人容器承载 ROS2 + FastAPI
- 前端打包后由 API 进程直接托管静态资源
- 通过 bind mount 或设备透传接入串口、摄像头、雷达
