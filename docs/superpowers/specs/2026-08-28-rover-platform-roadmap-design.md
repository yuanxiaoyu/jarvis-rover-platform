# 贾维斯小车平台分阶段路线图设计

- **日期**：2026-08-28
- **状态**：已确认设计
- **目标平台**：Yahboom MicroROS-Pi5、Raspberry Pi 5、ROS 2 Humble、micro-ROS、MS200 TOF 2D 雷达

## 1. 背景与问题定义

本项目需要在真实 Yahboom MicroROS-Pi5 环境上逐步实现：

1. 建图过程中底盘控制流畅，地图持续更新；
2. 建图暂停后可以在原地恢复，也可以在人工指定初始位姿后继续；
3. 采用接近成熟扫地机器人的边缘优先自主探索；
4. 提供实时 2D 地图、轻量 3D 空间视图和机器人控制台；
5. 通过语音完成单目标巡查、多步骤任务和对讲控制。

这些目标拆成多个有依赖关系的子项目。本设计先锁定系统边界和阶段出口，第一实现阶段是稳定建图与可恢复会话。

## 2. 已确认的真机事实

当前通过真机容器检查得到以下事实：

- 宿主机脚本 `~/ros2_humble.sh` 启动镜像 `yahboomtechnology/ros-humble:4.1.2`。
- 容器 `/root/1.sh` 启动 Supervisor；Supervisor 当前只管理底盘和 IP 服务。
- 底盘启动脚本运行 `ros2 launch yahboomcar_ctrl yahboomcar_joy_launch.py`。
- `YB_Car_Node` 发布 `/scan`、`/odom_raw`、`/imu`，并订阅 `/cmd_vel`。
- 手柄节点发布 `/cmd_vel`；因此后续必须引入明确的安全速度仲裁，不能让多个控制源无序竞争。
- 官方 `yahboomcar_bringup_launch.py` 启动 IMU 互补滤波、`robot_localization` EKF、机器人描述和 IMU 静态 TF，但不启动 SLAM。
- 官方工作区存在 Cartographer 和 GMapping 两套建图入口：
  - `yahboomcar_nav/map_cartographer_app_launch.xml`
  - `yahboomcar_nav/map_gmapping_app_launch.xml`
- 当前真机 shell 配置使用 `ROS_DOMAIN_ID=20`，项目示例配置默认使用 `30`，必须统一为 `20`。
- 当前 Cartographer 配置启用了在线相关扫描匹配并使用里程计；GMapping 配置的地图发布周期为 5 秒。两者都不能与新的主 SLAM 后端同时运行。

上述事实是运行时接入基线，不代表所有频率、时间戳、TF 外参和硬件 QoS 已经完成验收；阶段 0 必须把它们记录为版本化契约。

## 3. 设计决策

### 3.1 SLAM 后端

主路线采用 `slam_toolbox` 的 `online_async` 模式。保留官方 Cartographer 配置作为回退和对照基线，不在同一次运行中同时启动 Cartographer、GMapping 和 SLAM Toolbox。

选择原因：

- 需要暂停、保存、加载和增量继续建图；
- pose graph 序列化更适合会话恢复；
- 项目文档已经以 SLAM Toolbox 作为持续建图参考；
- 将会话管理封装在项目层后，Web、探索和语音可以复用同一任务契约。

SLAM Toolbox 的具体参数必须通过真机基准测试校准，不能直接将官方 Cartographer 或 GMapping 参数机械转换。

### 3.2 容器与 ROS 图边界

允许调整官方启动脚本和容器编排，但保留 Yahboom 节点作为硬件层。两个容器在同一个 ROS 2 网络中运行：

```text
Yahboom hardware container
  ├─ micro-ROS / YB_Car_Node
  ├─ /scan
  ├─ /odom_raw
  ├─ /imu
  └─ /cmd_vel

        │ ROS_DOMAIN_ID=20
        ▼

Jarvis mapping container
  ├─ robot_localization EKF       → /odom
  ├─ unified static TF             → robot frames
  ├─ slam_toolbox online_async     → /map, map→odom
  ├─ cmd_vel safety mux/watchdog   → hardware /cmd_vel
  └─ mapping session manager       → session state/persistence
```

硬件容器不承担 SLAM 会话管理。项目容器不重复启动硬件驱动，也不重复启动 EKF。所有容器必须显式配置 `ROS_DOMAIN_ID=20`。

必须满足以下唯一发布约束：

- 只有一个 EKF 发布 `odom -> base_footprint`；
- 只有一个 SLAM 后端发布 `map -> odom`；
- 只有一个安全速度仲裁器向 `YB_Car_Node` 输出最终 `/cmd_vel`；
- 同一时刻只运行一个 SLAM 后端。

官方 `yahboomcar_bringup_launch.py` 被视为定位/描述链路的一部分，不再被当作完整建图入口。生产默认不启动 RViz、rosbridge 和不必要的点云转换节点；这些作为调试或可选桥接能力运行。

## 4. 第一阶段：稳定建图与可恢复会话

### 4.1 目标与范围

第一阶段覆盖：

- 正常直行、转弯和低速遥控时地图持续更新；
- 原地暂停后恢复同一会话；
- 保存/加载地图和 pose graph；
- 人工搬运到已知地图位置后，通过 Web 或 RViz 指定初始位姿并继续建图；
- SLAM、项目容器、ROS 图或保存过程异常时安全停车并保留最后可用会话。

第一阶段不包含：

- 搬到任意位置后的自动无感重定位；
- 沿墙自主探索；
- 房间语义识别；
- 完整 Web 3D 控制台；
- Nav2 自主导航；
- 语音意图和任务编排。

### 4.2 运行链路

启动顺序固定为：

1. 硬件容器确认 micro-ROS、`YB_Car_Node` 和底盘输入正常；
2. 项目容器统一加载 ROS 2 和项目工作区；
3. 运行时预检确认 `/scan`、`/odom_raw`、`/imu`、必要 TF、磁盘和急停状态；
4. 启动唯一的 EKF，输出 `/odom`；
5. 发布并校验 `base_link -> laser_frame`、`base_link -> imu_frame` 等静态 TF；
6. 底盘保持停止，启动 `slam_toolbox online_async`；
7. SLAM 首次输出有效地图和位姿后，才进入可驾驶状态；
8. 安全速度仲裁器开放手柄或其他控制输入。

WebSocket、地图保存、日志和后续语音不能阻塞硬件控制、急停和安全 watchdog。

### 4.3 性能策略

控制链路优先于地图显示、媒体推送和语音：

- 硬件驱动和安全 watchdog 使用最高运行优先级；
- SLAM 使用独立进程；
- 地图序列化、压缩和 API 推送使用独立线程或进程；
- 语音模型默认关闭；
- 摄像头或浏览器拥塞时丢媒体帧，不反压 ROS 控制线程；
- 所有跨线程和 WebSocket 队列有界，客户端落后时丢弃旧地图/雷达快照；
- 不让旧扫描无限积压后集中处理。

厂商当前话题观测为 `RELIABLE + VOLATILE`。项目会显式配置与真机兼容的 QoS，并以“小队列、保留最新数据”为实时性原则：

- `/scan`：可靠、小深度、丢弃旧数据；
- `/odom_raw`、`/imu`：可靠、小队列；
- 地图：低频、可丢弃旧快照；
- WebSocket：有界背压，不影响 ROS 回调。

初始验证目标：

- 连续运行 30 分钟不发生 OOM、swap 抖动或明显热降频；
- 正常运行时最终控制指令间隔 p99 不超过 250 ms；
- 地图更新延迟 p95 不超过 2 秒；
- `/scan`、`/odom_raw`、`/imu` 相对空载基线的频率下降不超过 5%；
- 无持续 TF lookup、message filter 或时间戳错误。

这些是第一版门槛。阶段 0 测得真实基线后，只能根据数据收紧或合理修订，不能通过盲目降低控制或传感器频率来掩盖问题。

### 4.4 会话状态机

```text
IDLE
  └─ start → STARTING
STARTING
  ├─ 预检失败 → ERROR_RECOVERABLE
  └─ 预检通过 → MAPPING
MAPPING
  ├─ pause → PAUSED
  └─ stop → SAVING → IDLE
PAUSED
  ├─ resume → MAPPING
  ├─ save   → PAUSED
  └─ stop   → IDLE
任意运行态
  └─ 异常 → ERROR_RECOVERABLE
```

#### start

预检必须验证：

- `/scan` 有发布者并持续产生新数据；
- `/odom_raw` 和 `/imu` 时间戳单调、不过期；
- `base_footprint -> laser_frame` 可查询；
- `odom -> base_footprint` 由唯一 EKF 提供；
- 没有其他节点发布 `map -> odom`；
- 地图目录可写且有足够空间；
- 急停未触发；
- 底盘处于停止状态。

任何一项失败都不能进入 `MAPPING`。

#### pause/resume

暂停不是杀掉 SLAM 进程：

1. 安全层发布零速度；
2. 停止向 SLAM 会话交付新的测量；
3. 丢弃暂停期间积压的扫描；
4. 保存当前位姿和可恢复检查点；
5. 进入 `PAUSED`。

恢复时重新检查传感器、TF 和时间戳，确认底盘仍停止，恢复实时测量，进入 `MAPPING` 后再开放遥控。

#### save/load

一次会话至少持久化：

- `.pgm/.yaml` 占据栅格；
- SLAM Toolbox serialized pose graph；
- 会话参数和版本；
- `map/odom/base_footprint/laser_frame` 坐标约定；
- 地图分辨率、原点和尺寸；
- 最后有效位姿；
- 创建时间、硬件配置摘要和校验值；
- 会话状态。

保存使用临时文件、`fsync` 和原子重命名；保存失败时保留上一份完整会话，不覆盖最后可用版本。不会按每帧写入 SD 卡，只在显式保存、暂停检查点和低频 checkpoint 时写盘。

#### 搬运后恢复

第一阶段流程为：

1. 停止并保存会话；
2. 人工将小车搬到地图中的已知区域；
3. 在 Web 或 RViz 指定地图坐标和朝向；
4. 校验初始位置位于可通行区域；
5. 加载 pose graph；
6. 设置初始位姿；
7. 以低速短距离验证扫描匹配；
8. 验证通过后恢复建图。

恢复过程不自动发布运动指令。任意位置自动重定位属于后续阶段。

### 4.5 故障与安全行为

- SLAM 进程崩溃：安全层立即发零速度，会话进入 `ERROR_RECOVERABLE`；
- 缺少 `/scan` 或 TF：禁止恢复运动；
- 保存失败：保留旧会话并报告明确错误；
- API 断开：不接受新的运动任务，底盘 watchdog 独立停车；
- 项目容器重启：从最近完整 checkpoint 恢复为待确认状态，不自动行驶；
- 任何恢复流程都必须人工确认后才可重新开放运动。

## 5. 分阶段路线图

### 阶段 0：真机接口基线

工作内容：

- 固定 `ROS_DOMAIN_ID=20`；
- 记录 `/scan`、`/odom_raw`、`/imu`、`/cmd_vel`、`/battery` 的类型、频率、时间戳和 QoS；
- 确认完整 TF 树和坐标命名、雷达和 IMU 外参；
- 整理官方底盘容器与项目运行容器的启动/停止/健康检查/日志采集脚本；
- 录制一段 `rosbag2`，用于离线回归；
- 验证唯一 EKF、唯一 `map -> odom` 和唯一安全速度输出约束。

出口条件：不启动 SLAM 时，雷达、里程计、IMU 和底盘控制稳定运行，接口契约已版本化。

### 阶段 1：稳定建图与会话恢复

采用本设计第 4 节的 SLAM Toolbox 主链路、Cartographer 回退链路、会话状态机和安全策略。

出口条件：

- 30 分钟遥控建图无明显控制延迟；
- 地图持续更新；
- 原地暂停/恢复连续成功；
- 保存、加载和搬运后手动恢复通过；
- SLAM 或项目容器异常时自动停车；
- API/Web 负载不使控制指标恶化。

### 阶段 2：边缘优先自主探索

在稳定的 `/map`、`/odom`、TF 和安全层上实现：

1. 选择可见外墙或障碍边界；
2. 沿边界建立房间轮廓；
3. 在门口、拐角和边界断点生成候选前沿；
4. 通过 Nav2 到达可达前沿；
5. 继续边缘探索，直到没有足够置信度的未知边界；
6. 对不可达、重复或风险过高的候选点降级或放弃。

自定义探索器不能绕过 Nav2、keepout 和安全限速。

出口条件：能持续扩展地图，处理窄道、死胡同、动态障碍和暂时丢失边界，并输出探索进度和未探索前沿。

### 阶段 3：Web 控制台

#### 3A：2D 操作闭环

实现实时占据栅格、位姿、雷达叠加、图层开关、建图会话操作、手动初始位姿、虚拟墙、区域、任务状态、底盘控制、急停、连接状态、资源状态和告警。

#### 3B：轻量 3D 视图

3D 只从 2D 数据和语义区域推导，不声称是真实三维扫描：

- 墙体线段拉伸；
- 占据区域简化挤出；
- 房间/区域多边形；
- 低面数小车模型和轨迹；
- 稀疏当前雷达扫描层。

使用低面数几何、增量更新和视口裁剪。2D 是控制依据，3D 是理解和展示层。

出口条件：浏览器可观察和操作建图会话，断线重连能恢复状态，连续地图更新不会造成 API 内存无限增长。

### 阶段 4：语音对话与任务编排

处理链路：

```text
浏览器/本地麦克风
        ↓
ASR
        ↓
结构化意图解析
        ↓
任务计划
        ↓
区域、权限和安全校验
        ↓
必要时人工确认
        ↓
任务执行器
        ↓
状态回报 + TTS
```

第一版支持：去卧室巡查、先去卧室再去厨房、打开/关闭对讲、查询位置/电量/任务状态、语音取消/暂停/继续。所有自然语言必须转换为白名单结构化动作，模型不能直接生成未经校验的 ROS 命令。

树莓派默认采用按键说话或浏览器语音；本地唤醒词、ASR 和 TTS 只有在性能测试通过后才启用。

出口条件：单目标任务和多步骤任务均有明确确认、队列、当前步骤、失败步骤和取消行为；语音误识别不会直接触发危险运动。

## 6. 依赖与并行关系

```text
阶段 0 ───────► 阶段 1 ───────► 阶段 2
    │              │                │
    └──────────────► 阶段 3A ───────┘
                   │
                   └──────────────► 阶段 3B

阶段 1 的任务契约 ─────────────────► 阶段 4
```

Web 只读地图展示可以在阶段 1 期间并行开发；Web 控制、探索和语音任务必须使用阶段 1 定义的安全与会话接口。语音闭环不依赖 3D 视图，可以先在 2D 控制台完成。

## 7. 第一阶段验证矩阵

| 测试 | 通过条件 |
| --- | --- |
| ROS 图检查 | 节点、话题、TF 唯一且完整 |
| 空载基线 | 记录 CPU、温度、内存、雷达/里程计/IMU 频率 |
| 30 分钟遥控建图 | 控制响应稳定，地图持续更新 |
| 原地暂停恢复 | 连续 5 次恢复无地图断裂 |
| 保存/加载 | 连续 5 次保存和加载均可恢复 |
| 搬运恢复 | 指定初始位姿后能继续扩展地图 |
| 进程异常 | 自动停车，不破坏最后有效会话 |
| API/Web 负载 | 推送地图和雷达时控制指标不恶化 |
| 资源压力 | 无 OOM、swap 抖动或明显热降频 |

## 8. 非功能原则

- 先观测并固定接口，再优化算法；
- 先稳定遥控建图，再做自主探索；
- 先做 2D 控制闭环，再做 3D 展示；
- 先做结构化任务，再接入自然语言和语音；
- 自动能力不能绕过安全层；
- Web、语音或项目容器故障不能让小车继续失控运动；
- 2D MS200 雷达推导出的 3D 视图必须明确标注为重建展示，不得当作真实体积扫描结果。
